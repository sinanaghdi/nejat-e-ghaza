# پیاده‌سازی طراحی مرجع سهمینو

این سند توضیح می‌دهد چطور اصول موجود در `DESIGN.md` و چهار نمونهٔ HTML به رابط فعلی React متصل شده‌اند. نمونه‌های HTML برای استخراج ساختار بصری و نیازمندی‌ها استفاده شده‌اند؛ رفتارهای عملیاتی همچنان باید از API واقعی برنامه بیایند.

## سیستم طراحی

- **جهت و زبان:** فارسی، RTL و فونت Vazirmatn بارگذاری‌شده از بستهٔ پروژه. شناسه‌ها و مراجع فنی داخل `<bdi>` یا جهت LTR مجزا نمایش داده می‌شوند.
- **رنگ‌ها:** سبز جنگلی `#1B4332` برای اقدامات اصلی؛ سبز نعنایی برای حالت‌های مثبت؛ زعفرانی `#D97706` برای تخفیف و رزرو حساس به موجودی؛ پس‌زمینهٔ روشن `#F4F6F4` و کارت‌های سفید با خط مرزی ظریف.
- **قیمت:** قیمت جاری، قیمت اصلیِ خط‌خورده، تخفیف و واحد «تومان» در سلسله‌مراتب جدا. تعدادها و مبالغ از مقادیر API قالب‌بندی می‌شوند.
- **فاصله‌گذاری و شکل:** گام‌های نزدیک به مضارب ۸ پیکسل، شعاع ۸ تا ۲۴ پیکسل و سایه‌های کم‌عمق.
- **واکنش‌گرایی:** شبکهٔ سه‌ستونه در دسکتاپ، دو ستونه در تبلت و کارت‌های متراکم/ناوبری پایین در موبایل؛ پنل‌های فروشنده و مدیریت در موبایل به ناوبری افقی جمع می‌شوند.
- **دسترس‌پذیری:** برچسب‌های فرم، کنتراست، حالت focus قابل مشاهده، وضعیت‌های loading/error/empty، کنترل‌های واقعی به‌جای عناصر تزئینی و پشتیبانی از کاهش حرکت.

## تطبیق نمونه‌ها با صفحات واقعی

| نمونهٔ مرجع | پیاده‌سازی در اپ | منبع داده و رفتار |
|---|---|---|
| بازار و صفحهٔ آغازین | `HomePage`، `Header`، `OfferCard` | پیشنهادهای موجود در `useMarketplace`؛ دکمه‌های شهر/دسته‌بندی از طریق بارگذاری مجدد بازار عمل می‌کنند. |
| فهرست و فیلتر پیشنهادها | `OffersPage` | جست‌وجو، شهر، مرتب‌سازی و موقعیت نزدیک از مسیر `getOffers`؛ پاک‌کردن فیلترها همهٔ مقادیر را با هم بازنشانی می‌کند. |
| جزئیات بسته و رزرو | `OfferDetailPage` | موجودی، قیمت، توضیحات، نشانی فروشنده و بازهٔ دریافت از پیشنهاد واقعی. افزودن به سبد تنها سبد را تغییر می‌دهد؛ سفارش و پرداخت در مراحل موجود برنامه انجام می‌شوند. |
| میزکار فروشنده | `MerchantPage` و `MerchantDashboard` | پروفایل فروشگاه، پیشنهادها، سفارش‌ها، بررسی کد تحویل و دفتر تسویه از API موجود؛ ایجاد/ویرایش پیشنهاد از فرم فعلی استفاده می‌کند. |
| مرکز مدیریت | `AdminPage` | کاربران، احراز فروشگاه، تأیید پیشنهاد، سفارش‌ها، دفتر تسویه و صف بازپرداخت از API. فیلتر منطقه‌ای، خروجی CSV تسویه و ناوبری بخش‌ها نیز به پنل اضافه شده‌اند. |

## مرزهای عمدی: مواردی که نباید به‌صورت ساختگی نمایش داده شوند

- **نشان تأیید فروشنده:** کارت عمومی نشان تأیید را ادعا نمی‌کند، چون مدل پیشنهاد عمومی وضعیت احراز فروشنده را در خودش ندارد.
- **ترکیبات و آلرژن‌ها:** جزئیات فقط از توضیحات ثبت‌شدهٔ فروشنده نمایش داده می‌شود. رابط از مشتری می‌خواهد دربارهٔ دادهٔ ثبت‌نشده سؤال کند؛ ترکیبات یا گواهی بهداشتی تخیلی تولید نمی‌شود.
- **امتیاز و دیدگاه مشتریان:** مدل/مسیر API فعلی برای ثبت و خواندن دیدگاه‌ها در این رابط وجود ندارد؛ بنابراین امتیاز ستاره‌ای، شمار دیدگاه یا نظر نمونه به‌عنوان واقعیت نمایش داده نمی‌شود.
- **انتقال پول و بازپرداخت:** دفتر تسویه فقط مبلغ و مرجع ثبت‌شده را نشان می‌دهد. تأیید بازپرداخت در پنل مدیریت، مرجعِ بازپرداختی را ثبت می‌کند که قبلاً واقعاً از طریق بانک/درگاه انجام شده است؛ به‌خودی‌خود وجهی انتقال نمی‌دهد.
- **پیامک و پرداخت واقعی:** نسخهٔ عمومی GitHub Pages یک دموی UI است. به‌روزرسانی ظاهر هیچ‌یک از کلیدها، سرویس پیامک، اتصال API، HTTPS، هاست، پشتیبان‌گیری یا سیاست‌های عملیاتی را پیکربندی نمی‌کند.

## چک‌لیست بازبینی

- [ ] صفحهٔ اصلی در عرض‌های موبایل، تبلت و دسکتاپ بدون اسکرول افقی ناخواسته دیده شود.
- [ ] جست‌وجوی سربرگ با مسیر HashRouter به فهرست منتقل شود و عبارت جست‌وجو را اعمال کند.
- [ ] تغییر شهر و دسته‌بندی، درخواست بازار را با فیلتر مناسب بازبارگذاری کند.
- [ ] حالت‌های loading، خطا و خالی در فهرست و جزئیات قابل استفاده باشند.
- [ ] دکمهٔ افزودن به سبد با جریان فعلی سبد/ثبت سفارش سازگار بماند.
- [ ] فرم‌های فروشنده، تغییر وضعیت سفارش و تأیید تحویل از handlerهای موجود استفاده کنند.
- [ ] تغییر نقش/احراز فروشنده/مدیریت پیشنهاد/تسویه/بازپرداخت فقط به APIهای موجود ارسال شود.
- [ ] خروجی CSV از رکوردهای تسویهٔ فیلترشده ساخته شود.
- [ ] همهٔ ناوبری‌های پنل‌ها، از جمله خروج، در موبایل قابل دسترسی باشند.
- [ ] گردش‌کار CI شامل typecheck، audit، build، E2E، تست بک‌اند، اعتبارسنجی migration و build ایمیج‌های Docker موفق باشد.
- [ ] اجرای انتشار Pages جداگانه موفق شود؛ این کار با سبزشدن تست‌های مخزن یکی نیست.
- [ ] قبل از پایلوت واقعی، همهٔ گیت‌های `docs/pilot-readiness.md` و `SECURITY.md` با شواهد عملیاتی بررسی شوند.

## نکتهٔ نگهداری

لایهٔ CSS جدید در `frontend/src/reference-design.css` بعد از `styles.css` بارگذاری می‌شود تا ظاهر مشترک را بدون بازنویسی منطق درخواست‌های API تغییر دهد. اجزای فعلی React حفظ شده‌اند تا ظاهر جدید از مسیر واقعی عملیات استفاده کند.
